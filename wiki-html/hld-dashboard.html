Monet Technical Reference

A comprehensive guide to the Monet backend architecture, data flows, and REST API registry.

System Architecture Map

The Monet platform leverages a serverless Node.js/Express Lambda architecture. Clients hit a CloudFront distribution (which edge-caches the public card catalog and injects an origin secret) fronting an AWS HTTP API Gateway. A dedicated Lambda authorizer validates every protected request, and the main API Lambda (29s timeout, 1536 MB) reads/writes DynamoDB, integrates with Plaid for transactions, Google Places/Knowledge Graph for merchant resolution, and AWS Bedrock (Nova Micro) for AI bulk categorization.

Auth & Access Control

A single Lambda request authorizer (src/authorizer/handler.ts) guards all protected routes. Auth caching is disabled (resultTtlInSeconds: 0) because credential types are mutually exclusive and API Gateway would otherwise 401 valid requests. The authorizer accepts four credential types:

CredentialHeaderUsed by
Google ID tokenAuthorization: BearerSigned-in users (Google)
Apple JWTAuthorization: BearerSigned-in users (Apple)
Guest JWT (iss: monet-guest)Authorization: BearerGuests — minted by POST /v1/auth/guest
Dev API keyX-Dev-Api-KeyPostman / local dev only

Edge / origin protection

CloudFront injects a secret X-Origin-Secret header on every origin request; the authorizer rejects calls that lack it, so the API Gateway URL cannot be hit directly. Secrets (MONET_GUEST_JWT_SECRET, MONET_CUSTOM_JWT_SECRET, MONET_DEV_API_KEY, MONET_ORIGIN_SECRET, Plaid + Google keys) live in SSM Parameter Store. Plaid access tokens are encrypted at rest with AES-256-GCM (PLAID_ENCRYPTION_KEY, required at startup).

Public (unauthenticated) endpoints

These bypass the authorizer by design and are registered ahead of the catch-all:

  • GET /health — liveness ping.
  • POST /v1/auth/guest — the only public client-facing endpoint; mints a guest JWT.
  • POST /v1/plaid/webhook — Plaid verifies via its own payload signature, not a user token.
Client note The iOS app degrades gracefully without a session: it supports a guest flow and an on-device recommender (LocalRecommender + PlacesCache) so search/recommendations still work offline or before sign-in.

Key Data Flows

1. Authentication & Bootstrapping

The initial boot and synchronization flow, bringing the client up to date with the latest user profile, card wallet, and custom overrides via a single unified request.

The core path for determining the highest rewarding card for a specific merchant or broad category.

3. Plaid Insights Processing

A heavy computational background sync for downloading transactions, categorizing them, and generating historical spending insights and missed rewards.

The client-side API execution path in APIClient.swift which orchestrates retries, token refresh handshakes, rate limiting backoffs (dropping to offline LocalRecommender calculations), and server health checking loops.

DynamoDB Schema Map

The application follows a normalized repository pattern with multiple user-scoped tables, logically linked by a consistent partition key (userId).

MonetUsers

Field Type Description
id String (PK) Google OAuth subject identifier.
showGlobalBestCard Boolean Whether to surface market-best recommendations.
cards Map Keyed by cardId. Contains nicknames, last4, and custom reward rates.
plaidItems List Array of bank connections (itemId, encrypted accessToken, sync cursor).

MonetOverrides

Field Type Description
userId String (PK) Identifier of the user who owns this override.
merchantId String (SK) Cleaned, lowercased merchant name.
category String The pinned spending category.

MonetTransactions

Field Type Description
userId String (PK) Owner of the transaction.
transactionId String (SK) Plaid's unique transaction identifier.
date String ISO 8601 date. Range key for DateIndex LSI.
accountId String The Plaid account ID.
amount Number Transaction amount in USD.
merchantName String Cleaned merchant name from Plaid.
category String Monet-assigned spending category.
pending Boolean Whether the transaction is authorized but not settled.
primaryPersonalFinanceCategory String? Top-level Plaid enrichment category.

MonetInsightsCache

Field Type Description
userId String (PK) Owner of the cache entry.
cacheKey String (SK) Scope discriminator (e.g., "all" or "account:ID").
data Map Serialized insights payload.
ttl Number Unix epoch (seconds) for automatic expiration.
computedAt String ISO 8601 timestamp of computation.

MonetBrandCache

Caches resolved merchant→category decisions to avoid repeat Places/Bedrock calls. PK brandName. TTLs: confident mappings 365 days; OTHER/low-confidence (<0.5) 7 days.

MonetPlaidItemIndex

Reverse index itemId (PK) → userId. Avoids a full-table scan in getUserByItemId on every Plaid webhook (plaidItems is a nested Map and cannot be a GSI key).

Secondary indexes (Transactions)

MonetTransactions carries an LSI DateIndex (userId + date) plus GSIs MerchantNameIndex and CategoryIndex (each ranged by date). MonetOverrides has a MerchantIdIndex GSI. All tables are PAY_PER_REQUEST.

Rate Limits & Throttling

Throttling today lives entirely in the Express layer (src/middleware/rateLimit.ts). Limits are per client IP on a 60-second window and stored in-memory per warm Lambda instance — so effective ceilings scale with concurrency and are not globally shared. Exceeding a limit returns 429 with a Retry-After: 60 header. Disabled when NODE_ENV=test or DISABLE_RATE_LIMIT=true.

Backend ↔ iOS Contract

The backend (croe) and the iOS app (swift-app) share an implicit contract enforced only by matching string keys — there is no code generation. The canonical spending taxonomy lives in two hand-maintained places that must stay byte-identical on their raw values:

  • Backend: src/resources/categories.ts — enum Category (29 values incl. OTHER)
  • iOS: MonetApp/Models/Category.swift — String-backed Category enum (raw values = backend keys)
Safety net iOS decodes unknown category strings to .other (Category.swift), so responses never fail to parse. But a new category is invisible in UI lists, icons, labels, search, and reward maps until the iOS enum case is shipped.

Adding a new Category — required change ripple

Adding one enum value on the backend is never self-contained. The full sequence:

  1. Backend — add the case to categories.ts; wire getDisplayName() and MCC ranges in getCategoryDetails()/categoryFromMcc().
  2. Backend mapping — map Plaid PFC and/or brand rules to it in plaidCategoryMap.ts, brandCategoryMap.ts, and Places types in placesService.ts — otherwise it never gets assigned.
  3. Backend rewards — reference the new key in cardRewardsData.ts (rewards, specialRewards, allowedCategories) where cards earn on it.
  4. iOS enum — add the matching case to Category.swift with displayName, iconName, and optional synonyms. Category.allCases drives Browse, pickers, and search.
  5. iOS search — verify SearchView.swift / BusinessSearchService.swift autocomplete (iterates Category.allCases); update the hardcoded offline chips if the category should appear there.
  6. iOS grouping — place the category in a group in RecommendationCardView.swift (Travel / Everyday / Bills) or it falls into the .bills catch-all.
  7. iOS brands (optional) — add merchant rows to PopularBrands.swift (mirrors brandCategoryMap.ts).

Rotating / quarterly categories

Three SpecialReward shapes live in cardRewardsData.ts: RankedSpend rewards (e.g. Citi Custom Cash, Venmo, Zolve) carry allowedCategories + ranked tiers, with the applied tier resolved from the user's actual spend via Plaid insights (POST /v1/plaid/insights/sync → iOS InsightsManager.dynamicCardInsights); CategorySpecial rewards are fixed elevated rates with optional caps; and RotatingCategory rewards (Discover it, Freedom Flex) carry a per-quarter schedule that the optimizer resolves to the current calendar quarter by date (OptimizerContext.now overrides the date in tests). The quarterly cap is honored in both /recommend and insights — syncInsights.ts now populates OptimizerContext.categorySpend from calendar-period spend so capped rates demote correctly. iOS mirrors the type: SpecialReward.rotatingCategory decodes the schedule and activeCategories(on:) / Card.flattenedRotatingRewards resolve the current quarter for local calc and display. Remaining approximation: bonuses are optimistic re: activation (assumed active until the cap is hit), and the cap is tracked per-category rather than as the issuer's shared per-quarter pool.

Spend-cap evaluation (RankedSpend bypass + per-card spend)

All cap-bearing rewards now demote correctly in insights. Previously the autoRewards short-circuit in optimizer.ts returned the resolved RankedSpend tier (e.g. Citi Custom Cash 5%) without checking its cap; the optimizer now consults rankedSpendCapFor() in that branch and falls back to the base rate once the cap is reached. Caps are also evaluated per-card when possible: OptimizerContext.cardCategorySpend carries each linked card's own period-to-date spend (built in syncInsights.ts from plaidCardMappings), so a cap on a signed-in user's linked card is measured against that card's spend rather than the global category aggregate. Unlinked cards fall back to the global categorySpend. iOS decodes cap on base + special rewards (RewardCap) and CardDetailsView shows a faded disclaimer: caps are tracked from the card's linked transactions when linked, otherwise estimated from total category spending. Remaining gap: /recommend still uses the global aggregate (its fast cached path has no per-card spend).
